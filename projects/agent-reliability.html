EXECUTIVE SUMMARY

From automation to reliability engineering.

I worked on a production agentic AI system designed to automate SEO and web-operations workflows across e-commerce environments. The core challenge quickly shifted from task automation to reliability: I built validation tooling, investigated systemic agent failures, and introduced verification and human-approval mechanisms to prevent unsupported AI decisions from reaching production.

The work crossed agent orchestration, Python tooling, web extraction, API integrations, structured data, storefront operations and product workflow design. The result was a shift from LLM-driven automation toward evidence-driven agentic systems.

THE PROBLEM

Plausibility isn't reliability.

Agents could browse, extract, reason and act across messy external environments. But production execution exposed a fundamental problem: an agent can be confident, internally consistent, and completely wrong.

A missing field could actually be present. A failed request could be interpreted as missing data. A parser could silently discard information. An API could accept a write without the resulting change appearing publicly. A sample could be mistaken for a full-site finding.

The engineering question became less about making the agents more capable and more about making their decisions observable, testable and reversible.

THE DESIGN SHIFT

Don't tell the model to hallucinate less. Change the system around it.

01

Establish ground truth

Agent findings became hypotheses. Important claims were checked against directly fetched, parsed or independently queried source data.

02

Eliminate blind tools

Inspection tools had to expose the actual fields and evidence needed for a verdict rather than returning simplistic existence signals.

03

Make critical checks deterministic

Required fields, malformed responses, fetch failures, duplicates and incomplete outputs moved into executable validation where possible.

04

Protect production state

Existing data, destructive mutations, stale plans and customer-visible changes received explicit safeguards and verification gates.

05

Fix failure classes

When one agent exposed a shared defect, the same parser, fetch mechanism or logic was audited across the fleet instead of patching one symptom.

06

Escalate ambiguity

Automation was deliberately bounded by risk. High-impact or ambiguous actions could stop for human review rather than forcing an autonomous decision.

ARCHITECTURE

LLM reasoning sits inside a verification system.

The key architectural decision: the LLM proposes. Deterministic tooling verifies. Production access is gated by evidence.

A REAL FAILURE

When the agent said “missing” but the data said “present.”

One agent produced a high-severity finding that an organization's structured data contained no social profiles. The profiles were actually present.

The investigation uncovered multiple independent causes: the inspection tool exposed schema types but not their fields; the required field was not properly represented in the specification; an upstream audit was being loaded from an invalid path; and reviewer logic did not validate organization-level completeness.

The fix was therefore not another prompt instruction. The inspection layer was rebuilt to expose full keys, perform field-level validation, distinguish parse/fetch failures from absence, and produce an explicit entity-level verdict.

“An agent's failure report is a hypothesis — not evidence.”

OTHER FAILURE MODES

The system had to learn what “wrong” looks like.

Fetch failure ≠ missing data

Authentication walls, timeouts, rate limits, redirects and malformed responses were separated from genuine absence.

Stored ≠ rendered

An administrative read-back can prove a platform stored a value. It cannot prove customers or crawlers can see it.

Type exists ≠ field is correct

Structured-data validation moved from entity existence to actual attribute-level evidence.

Sample ≠ corpus

A finding from a small sample could not automatically be promoted into a claim about an entire site.

Generated ≠ factual

LLM-generated copy and claims required grounding in observable source material before production use.

Autonomous ≠ appropriate

Some production changes deliberately stopped at a human approval boundary because the cost of a wrong write was too high.

HUMAN-IN-THE-LOOP

Autonomy should be proportional to risk.

The goal was not maximum autonomy. It was appropriate autonomy.

Low-risk inspection could be heavily automated. Customer-visible mutations required stronger verification. Ambiguous or potentially destructive actions could stop for human review.

This produced a practical operating model: agent discovers → evidence validates → system gates → controlled action → live verification → human escalation when necessary.

WHAT I LEARNED

Reliable AI is a systems problem.

The most important lesson from the first month was that improving an agent does not necessarily mean improving its prompt.

Reliability emerged from the interaction between the model, tools, specifications, data sources, validators, deployment mechanisms and human operators.

The most useful question became:

“How does the system know that it is right — and what happens when it doesn't?”

TAKEAWAY

Don't build agents that only know how to act. Build agents that know when the evidence isn't good enough to act.
