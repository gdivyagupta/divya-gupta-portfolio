CASE STUDY / COMPUTER VISION · PRODUCT CONSTRAINTS

choosing less AI on purpose.

An anonymized technical product investigation into image processing architecture, where the best design depends on workload, latency, API limits, cost and operational control rather than model capability alone.

computer visionarchitectureapi constraintsproduct tradeoffs

THE QUESTION

where should vision processing happen?

the workflow needed to extract useful signals from product images inside a commerce environment. the initial instinct was to maximize parallel processing, but that introduced its own operational tradeoffs around concurrency, rate limits, compute and failure handling.

the product question became architectural: which parts should run in parallel, which should remain inline, and where would additional AI complexity actually improve the user outcome?

DECISION FRAMEWORK

optimize the workflow, not the number of AI calls.

01

workload

understand image volume, expected concurrency and the shape of the workload before choosing an execution model.

02

latency

parallelism can reduce wall-clock time, but only when the surrounding system can absorb the added concurrency.

03

api limits

rate limits and external service behaviour become product constraints when AI processing depends on third-party APIs.

04

failure recovery

a simpler execution path can be easier to observe, retry and debug when image processing fails partway through a workflow.

PRODUCT REASONING

technical elegance is not the same thing as product value.

i evaluated the architecture in terms of downstream decisions: what information the image processing actually needed to produce, how quickly it needed to arrive, what could safely fail, and how much operational complexity the team was willing to own.

that framing kept the conversation grounded in user outcome and system reliability rather than treating additional AI throughput as an objective by itself.
