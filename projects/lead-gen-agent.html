an agent that builds my outbound pipeline.

i wanted to turn lead generation from a repeated manual task into a system that can source, qualify, personalize, record and schedule outreach while keeping important decisions under human control.

the system

one workflow, several moving parts.

the pipeline uses apify to source leads, checks existing records in google sheets to avoid duplicates, uses gemini pro to generate personalized outreach, and writes the result back to the sheet before creating gmail drafts.

github actions provides the scheduled execution layer. the current workflow is configured for a daily run with a limit of 50 leads, while the sending step remains explicitly controlled through a repository-level permission.

architecture

apify → source and normalize prospects.

google sheets → maintain state and deduplicate contacts.

gemini → generate individualized outreach.

gmail → create drafts or send when explicitly authorized.

github actions → run the pipeline on a schedule.

the product decision

automation should have boundaries.

i deliberately separated automation from authorization. the pipeline requires confirmation of the active client profile, requires approval before exceeding the configured spend threshold, and keeps email sending behind an explicit send gate.

that means the system can automate repetitive work while preserving human control over targeting, money and outbound communication.

what i am learning

the interesting part of an agent is often the boundary between what it can do and what it should be allowed to do.

project

the code is public.

the repository contains the implementation, configuration structure and scheduled workflow. credentials and private operating data are kept outside the repository.
